# Fine-tuning dataset card

Generated by `python -m src.finetune.dataset_v4` (seed 20261127); files in `data/finetune_v4/` (not in git,
rebuilt in about a minute). No cloud LLM was used at any point.

**How a record is made.** Each record is a complete question-mode conversation, produced by the same code the live
system runs (`src/harness/question_mode.py`): the same system prompt (rules and allowed actions), the same 15 MCP
tool definitions, real tool outputs under the analysis-date ceiling, shown in the same compact view. Questions come
from hand-written Turkish phrasings filled with sampled tickers, sectors, periods and analysis dates (2024-03 to
2026-11). The gold tool calls are fixed by the question; the answer is written by Python templates
(`src/finetune/templates.py`) from the tool outputs, and its action follows the pre-written rules. Every answer must
pass the system's own checks (no number outside tool outputs, no advice/target price, allowed action) or it is not
kept. A test replays every conversation through question mode and gets the same tool outputs, checks and action.

**Coverage.** Four mandatory scenarios (sector laggard / catch-up, weekday and multi-day patterns, technical
reversals, quarterly fundamentals and price reaction), safety questions (advice, target price, "it will surely
rise" claims), single uses of the other tools, and error cases (unknown ticker / index / sector, questions about
dates after the analysis date). The instructor's five sample questions are included verbatim in training, so the
evaluation uses separate held-out questions. Random sampling gave only 5 catch-up and 6 technical-reversal
candidates, so 100 targeted examples were added: same rules, only stocks and dates where the rule
holds were searched.

**v4 changes** (on top of v3). (1) 60 *error-fix* conversations: the first suitable tool call is deliberately
broken (wrong strategy/event/condition/indicator name, malformed weekday pattern, out-of-range out-of-sample date,
swapped dates, ticker with a `.IS` suffix, a quarter name instead of a date), the real tool error comes back, the
next turn is the corrected call and the answer is normal. The broken call stays in the context but is excluded from
the loss, so the model learns the correction, not the mistake. Error questions (unknown ticker/index/sector, future
dates) still end with ANALYSIS_UNSAFE. In v3 all 24 conversations with a tool error ended with ANALYSIS_UNSAFE and
20 of v3's 28 wrong evaluation answers were ANALYSIS_UNSAFE. (2) Weekday patterns are described by generated
sentences (day names, "first/last two days of the week", "the next day"; three word families, three sentence shapes)
for every single-direction condition/outcome pattern, not only 8; new phrasings give the out-of-sample period first
or ask about "N sessions in a row". (3) Exchange-rate claims over a period shorter than 60 trading days (the tool
cannot estimate the relation) end with INVESTIGATE; more claims without a period (the call starts at 2024-01-01).
(4) The system prompt now says: fix and retry a correctable tool error; no period given -> start 2024-01-01;
fundamentals questions use only their three actions; an unestimable relation means the claim is not supported.
Phrasings of the second held-out set (`heldout_v3.py`) are not used in training; v4 is evaluated on a new set.

**Training format.** MLX `chat` format (`{"messages": [...], "tools": [...]}`). MLX with `mask_prompt` learns only
the last assistant message, so each conversation is split into one example per assistant turn (tool-call turns and
the final answer).
